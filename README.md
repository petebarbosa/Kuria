# Kuria

A personal finance app for multi-currency tracking, budgeting, and investment management. Built on Rails 8.

## Features

- **Account tracking** — bank accounts, credit cards, investments, loans, properties, vehicles, and crypto
- **Multi-currency support** — track balances and transactions across currencies with exchange rate data
- **Transaction management** — categorization, tagging, bulk editing, auto-classification rules, and merchant resolution with aliases
- **Budgets** — monthly budget planning and tracking
- **Investment portfolio** — holdings, valuations, and performance tracking
- **AI financial assistant** — conversational assistant with access to your financial data. AI runs exclusively through RubyLLM against hosted OpenAI and OpenCode Go APIs (no OpenCode Server). The model is chosen explicitly per chat from the models currently available for your configured credentials — there is no default and no automatic fallback.
- **Merchant intelligence** — automatic merchant name normalization, tiered matching resolver, and AI-powered merchant suggestions
- **Imports** — CSV import, Plaid bank sync, and Mint data migration
- **Data exports** — export your data at any time
- **Self-hostable** — run it yourself with Docker
- **Payments feature flag** — disable Stripe/subscription billing entirely for self-hosted use (`PAYMENTS_ENABLED=false`)

## Local Development Setup

### Requirements

- Docker (recommended: runs the full development stack)
- Ruby 4.0.7 (see `.ruby-version`) and Bundler (`gem install bundler`) only for the host-based workflow

### Development with Docker (recommended)

`compose.dev.yml` builds `Dockerfile.dev` and runs the complete development stack:

| Service  | Purpose                               |
| -------- | ------------------------------------- |
| `web`    | Rails server on port 3000             |
| `css`    | Tailwind CSS watcher                  |
| `worker` | Sidekiq background jobs               |
| `db`     | PostgreSQL (same image as production) |
| `redis`  | Redis (same image as production)      |

```sh
docker compose -f compose.dev.yml up --build
```

On the first run, create and migrate the development database from another terminal:

```sh
docker compose -f compose.dev.yml run --rm web bin/rails db:create db:migrate
```

The source tree is bind-mounted at `/rails`, so code changes are picked up live. The Compose project is named `kuria-dev`; its containers, network, and volumes are separate from the production stack. `POSTGRES_DB` is forced to `kuria_development` in this file even if `.env` sets a production database.

Stop the stack with:

```sh
docker compose -f compose.dev.yml down      # keeps the development volumes
```

If the production stack is already using port 3000, stop it first **without** `-v`/`--volumes` (for example, `docker compose -f compose.yml down`), then start the development stack. Never run `down -v` against production volumes.

### Host-based Rails (optional)

To keep Rails, Tailwind, and Sidekiq on the host while running only PostgreSQL and Redis in Docker:

```sh
git clone https://github.com/petebarbosa/kuria.git
cd kuria
cp .env.example .env        # only if .env does not exist; set SECRET_KEY_BASE
docker compose -f compose.dev.yml up -d db redis
bin/setup                   # installs gems, creates DB, runs migrations
bin/dev                     # starts Rails, Tailwind, and Sidekiq on the host
```

For this workflow keep `DB_HOST`/`DB_PORT` and `REDIS_URL` pointed at localhost (the dev compose file publishes PostgreSQL and Redis on `127.0.0.1`; use `127.0.0.1` directly if `localhost` resolves to IPv6 first on your machine), and leave `POSTGRES_DB` unset or set it to `kuria_development` so host Rails uses the isolated development database.

`bin/dev` starts three processes concurrently:

- Rails server on port 3000
- Tailwind CSS watcher
- Sidekiq worker for background jobs

Visit [http://localhost:3000](http://localhost:3000). Default credentials generated by the seed:

- Email: `user@kuria.local`
- Password: `password`

### Demo data

```sh
rake demo_data:default        # Full realistic dataset
rake demo_data:empty          # Empty family (no financial data)
rake demo_data:new_user       # New user family (needs onboarding)
```

### Tests

```sh
bin/rails test          # unit and integration tests
bin/rails test:system   # browser-based system tests
```

Test environment uses its own database (`kuria_test`) and Redis namespace. Configure with `.env.test` or `.env.test.example`.

### Pre-commit checks

The repo uses [Husky](https://typicode.github.io/husky/) git hooks. Run `npm run prepare` once (npm also runs it automatically after `npm install`) to install the hooks.

The `pre-commit` hook runs `lint-staged`, which processes only staged files:

- **Prettier** — all staged files are formatted with `prettier --ignore-unknown --write`
- **RuboCop** — staged Ruby and Rake files are additionally linted with `bin/rubocop --force-exclusion`

Both need their dependencies installed (Node packages via `npm install`, Ruby gems via `bundle install`) for the hook to run.

## Self-Hosting with Docker

See [`docs/hosting/docker.md`](docs/hosting/docker.md) for the full guide.

The production compose file (`compose.example.yml`) includes:

| Service  | Description             |
| -------- | ----------------------- |
| `web`    | Rails app (port 3000)   |
| `worker` | Sidekiq background jobs |
| `db`     | PostgreSQL 16           |
| `redis`  | Redis 7                 |

All services run on the `kuria_network` bridge network.

> **AI provider:** AI runs exclusively through RubyLLM, calling hosted OpenAI and OpenCode Go APIs directly (`OPENAI_API_KEY` and/or `OPENCODE_GO_API_KEY`). Provider keys are supplied through the environment (or encrypted deployment credentials) and are never stored in ordinary application settings. No OpenCode Server container is required or started. The selectable models are listed from each configured provider at configuration/selection time; there is no default model and no hardcoded list, the model is selected explicitly per chat, and an unavailable selection requires reselection rather than silent replacement. Assistant requests are rate limited per authenticated user (web and API) at `ASSISTANT_REQUESTS_PER_HOUR` requests per hour, defaulting to 100 in both managed and self-hosted modes; over-limit requests are rejected before any provider work. Historical OpenCode data is retained and no history is deleted. Features still deferred to their tracked issues are listed in [Known capability gaps](#known-capability-gaps-deferred).

> **Transaction enrichment model:** Financial enrichment (auto-categorization and merchant detection/suggestion) reuses the same provider credentials and is configured by an administrator under **Settings → Account → Transaction enrichment model**, which saves the choice on the Family. There is no default model: the selector lists the models currently available for the configured provider credentials, the saved selection is the only model enrichment uses, and a saved model that is no longer available fails safely and requires reselection rather than a silent fallback. As with chat, provider keys come from the environment or encrypted deployment credentials and are never stored in ordinary application settings.

At minimum you will need to set the following environment variables:

| Variable                      | Description                                                                                                                                  |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `SECRET_KEY_BASE`             | Required. Generate with `openssl rand -hex 64`.                                                                                              |
| `SELF_HOSTED`                 | Set to `true` to enable self-hosting mode.                                                                                                   |
| `PAYMENTS_ENABLED`            | Set to `false` to disable Stripe/subscription billing (all accounts treated as paid).                                                        |
| `SYNTH_API_KEY`               | Security market data provider (optional).                                                                                                    |
| `FREECRYPTO_API_KEY`          | Crypto exchange-rate snapshots via FreeCryptoAPI (optional; historical crypto unsupported on free tier).                                     |
| `OPENAI_API_KEY`              | Optional. Enables `openai/<model>` selection; models are listed from the provider at selection time, not hardcoded.                          |
| `OPENCODE_GO_API_KEY`         | Optional. Enables `opencode_go/<model>` selection; models are listed from the provider at selection time, not hardcoded.                     |
| `ASSISTANT_REQUESTS_PER_HOUR` | Optional. Per-authenticated-user assistant request allowance (web and API), in requests per hour, enforced in both modes; defaults to `100`. |
| `MCP_AUTH_TOKEN`              | Optional. Bearer token for the independent MCP endpoint (`POST /mcp`); separate from the retired OpenCode Server LLM path.                   |
| `SMTP_*`                      | Mail delivery configuration (optional).                                                                                                      |

### Implemented assistant capability

- **#11:** The RubyLLM assistant reads the authenticated Family's accounts through the direct, read-only `get_accounts` tool. The server binds the Family; the model cannot select or supply a family id. Attempted calls are audited before execution.

### Known capability gaps (deferred)

The RubyLLM-only cutover is **not complete**. The capabilities below are explicitly deferred to their tracked issues and are **not** claimed as working parity with the former OpenCode Server path:

| Issue | Deferred capability                                                         |
| ----- | --------------------------------------------------------------------------- |
| #10   | Guarantee ordered RubyLLM streaming and reload parity                       |
| #12   | Reconstruct three-turn conversations from persisted history                 |
| #13   | Propose a Transaction without mutating financial data                       |
| #14   | Confirm a proposed Transaction exactly once                                 |
| #15   | Run one categorization workflow through RubyLLM Schema                      |
| #16   | Recover safely from RubyLLM provider failures                               |
| #17   | Rate-limit authenticated Assistant requests per user                        |
| #18   | Emit privacy-safe Assistant telemetry                                       |
| #19   | Add optional live OpenAI and OpenCode Go compatibility smoke tests          |
| #30   | Migrate merchant detection and suggestions to the RubyLLM provider contract |

Unsupported capabilities fail safely: they surface through the existing provider response/error path — a failed response, a form alert, or a rejected model selection — and never report placeholder success or silently substitute a model. Financial enrichment that is not yet migrated (auto-categorization, merchant detection, and merchant suggestion) currently returns a failed provider response rather than performing the work.
