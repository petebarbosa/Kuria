# Kuria

A personal finance app for multi-currency tracking, budgeting, and investment management. Built on Rails 8.

## Features

- **Account tracking** — bank accounts, credit cards, investments, loans, properties, vehicles, and crypto
- **Multi-currency support** — track balances and transactions across currencies with exchange rate data
- **Transaction management** — categorization, tagging, bulk editing, auto-classification rules, and merchant resolution with aliases
- **Budgets** — monthly budget planning and tracking
- **Investment portfolio** — holdings, valuations, and performance tracking
- **AI financial assistant** — conversational assistant with access to your financial data. AI runs exclusively through RubyLLM against hosted OpenAI and OpenCode Go APIs (no OpenCode Server or local OpenCode runtime). The model is chosen explicitly per chat from the models currently available for your configured credentials — there is no default and no automatic fallback.
- **Merchant intelligence** — automatic merchant name normalization, tiered matching resolver, and AI-powered merchant suggestions
- **Imports** — CSV import, Plaid bank sync, and Mint data migration
- **Data exports** — export your data at any time
- **Self-hostable** — run it yourself with Docker
- **Payments feature flag** — disable Stripe/subscription billing entirely for self-hosted use (`PAYMENTS_ENABLED=false`)

## Local Development Setup

### Requirements

- Docker (recommended: runs the full development stack)
- Ruby 4.0.9 (see `.ruby-version`) and Bundler (`gem install bundler`) only for the host-based workflow

### Development with Docker (recommended)

`compose.dev.yml` builds `Dockerfile.dev` and runs the complete development stack:

| Service  | Purpose                               |
| -------- | ------------------------------------- |
| `web`    | Rails server on port 3000             |
| `css`    | Tailwind CSS watcher                  |
| `worker` | Sidekiq background jobs               |
| `db`     | PostgreSQL (same image as production) |
| `redis`  | Redis (same image as production)      |

```sh
docker compose -f compose.dev.yml up --build
```

On the first run, create and migrate the development database from another terminal:

```sh
docker compose -f compose.dev.yml run --rm web bin/rails db:create db:migrate
```

The source tree is bind-mounted at `/rails`, so code changes are picked up live. The Compose project is named `kuria-dev`; its containers, network, and volumes are separate from the production stack. `POSTGRES_DB` is forced to `kuria_development` in this file even if `.env` sets a production database.

Stop the stack with:

```sh
docker compose -f compose.dev.yml down      # keeps the development volumes
```

If the production stack is already using port 3000, stop it first **without** `-v`/`--volumes` (for example, `docker compose -f compose.yml down`), then start the development stack. Never run `down -v` against production volumes.

### Host-based Rails (optional)

To keep Rails, Tailwind, and Sidekiq on the host while running only PostgreSQL and Redis in Docker:

```sh
git clone https://github.com/petebarbosa/kuria.git
cd kuria
cp .env.example .env        # only if .env does not exist; set SECRET_KEY_BASE
docker compose -f compose.dev.yml up -d db redis
bin/setup                   # installs gems, creates DB, runs migrations
bin/dev                     # starts Rails, Tailwind, and Sidekiq on the host
```

For this workflow keep `DB_HOST`/`DB_PORT` and `REDIS_URL` pointed at localhost (the dev compose file publishes PostgreSQL and Redis on `127.0.0.1`; use `127.0.0.1` directly if `localhost` resolves to IPv6 first on your machine), and leave `POSTGRES_DB` unset or set it to `kuria_development` so host Rails uses the isolated development database.

`bin/dev` starts three processes concurrently:

- Rails server on port 3000
- Tailwind CSS watcher
- Sidekiq worker for background jobs

Visit [http://localhost:3000](http://localhost:3000). Default credentials generated by the seed:

- Email: `user@kuria.local`
- Password: `password`

### Demo data

```sh
rake demo_data:default        # Full realistic dataset
rake demo_data:empty          # Empty family (no financial data)
rake demo_data:new_user       # New user family (needs onboarding)
```

### Tests

```sh
bin/rails test          # unit and integration tests
bin/rails test:system   # browser-based system tests
```

Test environment uses its own database (`kuria_test`) and Redis namespace. Configure with `.env.test` or `.env.test.example`.

### Pre-commit checks

The repo uses [Husky](https://typicode.github.io/husky/) git hooks. Run `npm run prepare` once (npm also runs it automatically after `npm install`) to install the hooks.

The `pre-commit` hook runs `lint-staged`, which processes only staged files:

- **Prettier** — all staged files are formatted with `prettier --ignore-unknown --write`
- **RuboCop** — staged Ruby and Rake files are additionally linted with `bin/rubocop --force-exclusion`

Both need their dependencies installed (Node packages via `npm install`, Ruby gems via `bundle install`) for the hook to run.

## Self-Hosting with Docker

See [`docs/hosting/docker.md`](docs/hosting/docker.md) for the full guide.

The production compose file (`compose.example.yml`) includes:

| Service  | Description             |
| -------- | ----------------------- |
| `web`    | Rails app (port 3000)   |
| `worker` | Sidekiq background jobs |
| `db`     | PostgreSQL 16           |
| `redis`  | Redis 7                 |

All services run on the `kuria_network` bridge network.

> **AI provider:** AI runs exclusively through RubyLLM, calling hosted OpenAI and OpenCode Go APIs directly (`OPENAI_API_KEY` and/or `OPENCODE_GO_API_KEY`). Provider keys are supplied through the environment (or encrypted deployment credentials) and are never stored in ordinary application settings. No OpenCode Server container or local OpenCode runtime is required or started. Both accounts use OpenAI-compatible Chat Completions only; Responses-only, Anthropic Messages, and Gemini model references are rejected and never translated to another protocol. The selectable models are the verified Chat Completions catalog intersected with each configured account's live model list; there is no default model, the model is selected explicitly per chat, and an unavailable selection requires reselection rather than silent replacement. Assistant requests are rate limited per authenticated user (web and API) at `ASSISTANT_REQUESTS_PER_HOUR` requests per hour, defaulting to 100 in both managed and self-hosted modes; over-limit requests are rejected before any provider work. Historical OpenCode data is retained and no history is deleted. Features still deferred to their tracked issues are listed in [Known capability gaps](#known-capability-gaps-deferred).

> **Transaction enrichment model:** Financial enrichment (auto-categorization and merchant detection/suggestion) reuses the same provider credentials and is configured by an administrator under **Settings → Account → Transaction enrichment model**, which saves the choice on the Family. There is no default model: the selector lists the models currently available for the configured provider credentials, the saved selection is the only model enrichment uses, and a saved model that is no longer available fails safely and requires reselection rather than a silent fallback. As with chat, provider keys come from the environment or encrypted deployment credentials and are never stored in ordinary application settings.

At minimum you will need to set the following environment variables:

| Variable                      | Description                                                                                                                                  |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `SECRET_KEY_BASE`             | Required. Generate with `openssl rand -hex 64`.                                                                                              |
| `SELF_HOSTED`                 | Set to `true` to enable self-hosting mode.                                                                                                   |
| `PAYMENTS_ENABLED`            | Set to `false` to disable Stripe/subscription billing (all accounts treated as paid).                                                        |
| `SYNTH_API_KEY`               | Security market data provider (optional).                                                                                                    |
| `FREECRYPTO_API_KEY`          | Crypto exchange-rate snapshots via FreeCryptoAPI (optional; historical crypto unsupported on free tier).                                     |
| `OPENAI_API_KEY`              | Optional. Enables `openai/<model>` selection; models are the verified catalog intersected with the provider's live list.                     |
| `OPENCODE_GO_API_KEY`         | Optional. Enables `opencode_go/<model>` selection; models are the verified catalog intersected with the provider's live list.                |
| `ASSISTANT_REQUESTS_PER_HOUR` | Optional. Per-authenticated-user assistant request allowance (web and API), in requests per hour, enforced in both modes; defaults to `100`. |
| `MCP_AUTH_TOKEN`              | Optional. Bearer token for the independent MCP endpoint (`POST /mcp`); separate from the RubyLLM provider path.                              |
| `SMTP_*`                      | Mail delivery configuration (optional).                                                                                                      |

### Implemented assistant capability

- **#11:** The RubyLLM assistant reads the authenticated Family's accounts through the direct, read-only `get_accounts` tool. The server binds the Family; the model cannot select or supply a family id. Attempted calls are audited before execution.
- **#12:** The RubyLLM assistant reconstructs conversation history from persisted records: user messages, non-debug Developer messages (replayed as system preamble), and completed non-reasoning assistant answers, including completed tool rounds. Reconstruction is normalized from persisted final answers and audit outcomes rather than the model's exact intermediate tool-round text; ambiguous or incomplete completed tool audits fail safely instead of silently omitting history.
- **#13:** The RubyLLM assistant can prepare a new transaction through the server-bound `propose_transaction` tool. It creates a `PendingAction` with a 10-minute TTL and preview and returns a `pending_confirmation` result; it never creates or mutates a transaction. Family/user scope is bound server-side, model-supplied scope ids are rejected, and idempotent retries return the same proposal. Confirmation happens through the authenticated endpoint described under **#14**.
- **#14:** A prepared proposal is confirmed exactly once through the authenticated `POST /pending_actions/:id/confirm` endpoint. The first confirmation executes the transaction once and records the confirming user and the execution status on both the pending action and its tool-call audit. Replays return `422` with reason `already_confirmed`, expired proposals return `422` with reason `expired`, and a proposal belonging to another family returns `404`; none of these execute again. If execution itself fails, the response is `422` with `status: "confirmed"` and `execution_status: "failed"`. There are no in-chat confirmation controls yet — the assistant exposes no confirmation tool and the chat UI renders no confirm action — so confirmation is endpoint-based only; the `pending_confirmation` result carries the `pending_action_id` and preview.
- **#18:** The Assistant emits one privacy-safe `assistant.request.kuria` terminal event per request to `ActiveSupport::Notifications` and the structured info log. Its strict allowlist is `event`, `message_id`, `chat_id`, `provider`, `model`, `outcome`, `latency_ms`, `retry_count`, `usage` (`input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `reasoning_tokens`), `estimated_cost` (`usd`, `known`, `source`, `reason`), `tool_outcomes` (`succeeded`, `rejected`, `failed`), `error_class`, and `error_retryable`. Prompts, completions, tool results, credentials, and provider bodies are never included, and ids are validated. Cost is known only for OpenAI models in the installed RubyLLM `2.1.1` bundled pricing registry (source `ruby_llm_bundled_registry`); OpenCode Go estimates stay `usd: nil, known: false` with a reason because Kuria has no authoritative Go account/window pricing source (Go publishes peak/off-peak windows), and unknown is never reported as zero.
- **#19:** Optional live OpenAI/OpenCode Go compatibility smoke tests are opt-in only: `KURIA_LIVE_LLM_TESTS=1` plus explicit `KURIA_LIVE_OPENAI_MODEL=openai/<model>` and `KURIA_LIVE_OPENCODE_GO_MODEL=opencode_go/<model>`; credentials are gated and read only from the `OPENAI_API_KEY` / `OPENCODE_GO_API_KEY` environment variables. Run `DISABLE_PARALLELIZATION=true bin/rails test test/live`; see [`test/live/README.md`](test/live/README.md). The raw HTTP harness (`llm_compatibility_test.rb`) covers protocol details plus one OpenAI production-seam developer-instructions check; the production-seam harness (`ruby_llm_compatibility_test.rb`) adds streamed-vs-final content consistency, actual local tool execution, strict structured synthetic categorization, and independent OpenAI/Go selection. These are harness capabilities, not results: live validation has not been run in this checkout, so no Go parity is claimed. The harness targets installed RubyLLM `2.1.1` and the tests are skipped without the flag (routine CI). Direct HTTP checks are protocol evidence only; the production-seam checks are adapter coverage.

### Known capability gaps (deferred)

Remaining capability parity is **incomplete**. The capabilities below are explicitly deferred to their tracked issues and are **not** claimed as working parity:

| Issue | Deferred capability                             |
| ----- | ----------------------------------------------- |
| #21   | Produce the RubyLLM readiness acceptance report |

The former OpenCode Server provider integration has been retired from this checkout: the legacy `opencode/` provider classes, their tests, and the `opencode_server_*` / `opencode_default_model` settings are removed. Hosted **OpenCode Go** (`opencode_go/<model>` via RubyLLM and `OPENCODE_GO_API_KEY`) remains supported alongside OpenAI. Historical OpenCode data is retained — `chats.opencode_session_id`, `chats.latest_assistant_response_id`, and the `opencode-config` volume are deliberately preserved — and the independent `POST /mcp` endpoint is unrelated to any LLM provider. Issue #31 is implemented in this checkout but remains **open pending review and merge**; it is not claimed closed or shipped.

Unsupported capabilities fail safely: they surface through the existing provider response/error path — a failed response, a form alert, or a rejected model selection — and never report placeholder success or silently substitute a model. Transaction enrichment (auto-categorization, merchant detection, and merchant suggestion) runs through RubyLLM structured output (#15 and #30 are closed), but it still requires an explicitly saved enrichment model and fails safely when that model is unavailable.
